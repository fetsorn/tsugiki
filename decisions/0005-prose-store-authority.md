# Prose store replaces Fountain as authority

## Context and Problem Statement

ADR-0001 established a dual authority: CSVS tablets are authority on the DAG (containment, bridges), Fountain files are authority on prose content. This split worked for the prototype, but CSVS 0.0.4 introduced a prose store — any value in any tablet can have a prose description, stored as a plain text blob alongside the tablets.

With the prose store available, Fountain files become redundant as an authority. They duplicate information (prose keyed by UUID) in a format that requires parsing, and every write command must transform a Fountain file line-by-line. Meanwhile, the prose store offers direct UUID-to-text lookup with no parsing.

The prototype (Layer -1) confirmed that the three-tree model and the workflow are sound. The remaining commands (init, split, regrow, render) have not been built yet. This is the right moment to shift the storage layer before more code depends on Fountain-as-authority.

## Decision

### CSVS is sole authority

CSVS tablets are authority on the DAG — unchanged from ADR-0001.

CSVS prose store is authority on text content. Each node UUID that appears in any tablet can have a prose blob at `csvs/prose/{uuid}`. The blob is plain UTF-8 text. No headers, no metadata — just the content.

- **Source node prose**: the source text (sentence, paragraph, heading title).
- **Structure node prose**: the annotation text, optionally followed by translator notes. Notes use the same Fountain-era markers inside the blob: `[[note text]]` for annotate-phase notes, `[[| note text]]` for regrow-phase notes, each on its own line after the annotation.
- **Target node prose**: the translated text.

A node with no prose blob has empty content (equivalent to an empty annotation in the old model).

### Fountain files are rendered views

`source.fountain`, `structure.fountain`, `target.fountain` are generated by `tsugiki render`, not written directly. They are assembled by walking the containment tree (from `-child.csv` tablets) in depth order, looking up prose for each UUID, and emitting Fountain format.

Rendered files live in `prose/` as convenience artifacts. They may be committed as snapshots or generated on demand. They are never read by CLI commands as a data source.

`source.md` and `target.md` are also rendered views — clean markdown stripped of UUIDs and notes.

### CLI commands read and write the prose store

- `init` parses markdown, generates UUIDs, writes tablets and prose blobs.
- `show` and `next` read tablets and prose blobs directly. No Fountain scanning.
- `annotate` writes (or overwrites) the prose blob for a structure node UUID.
- `split` modifies containment tablets, retires the original prose blob, creates new prose blobs for the fragments.
- `regrow` creates a target node UUID, writes its prose blob, appends to bridge and containment tablets.
- `render` assembles Fountain and/or markdown from tablets and prose store.

### Dataset version

`.csvs.csv` changes from:
```
version,0.0.3
id,{v4-uuid}
```
to:
```
csvs,0.0.4
uuid,{v4-uuid}
```

### Migration from 0.0.3

Existing intents (like cong1) migrate by:
1. Bumping `.csvs.csv` to the new format.
2. Extracting prose from Fountain files into `csvs/prose/{uuid}` blobs — one blob per node, keyed by the full UUID from the tablets.
3. Fountain files in `prose/` become generated. The originals can be archived or deleted.

Tablet format is unchanged — only the version line and prose store addition.

## Consequences

- Single authority eliminates the "if they disagree, CSVS wins on structure, Fountain wins on content" rule. There is nothing to disagree — CSVS is the only store.
- Every CLI command becomes a direct read/write on tablets and prose blobs. No Fountain parsing on the read path. No streaming line-by-line file transformations for writes.
- `show` resolves a UUID by reading `csvs/prose/{uuid}` — one filesystem read, no regex.
- `annotate` writes `csvs/prose/{uuid}` — one filesystem write, no temp-file-and-rename.
- Fountain files can still be generated for human reading, editor integration, or export. The `render` command serves this purpose.
- Notes lose no expressiveness — they live inside the structure prose blob with the same `[[]]` markers. The blob is just text; the markers are a convention for the render command to parse when assembling Fountain output.
- The addressing model (line number, short hex, full UUID) narrows. Line numbers only make sense in rendered Fountain files. For CLI commands operating on the prose store, hex IDs and full UUIDs are the primary addresses. Line numbers can still work if the user has a rendered file open — the CLI resolves them by scanning the rendered file, then maps to UUIDs.
